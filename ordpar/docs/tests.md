# The site's tests

Every test of the site lives in `ordpar/tests/`
(decisions [101](../../docs/decisions.md#d101)): one `test_ordpar_*.py` file per decision or
feature, written with the standard library's `unittest`, no pytest. Each file's docstring says what
it pins; the table at the end of this page is the index. **A change that adds a test file adds its
row to the table.**

## Running them

From the repository root, with the data in `data/` and its articles joined once after a clone or
a pull:

```bash
python ordpar/data_parts.py join data/bokmalsordboka
export ORDBOK_DATA_DIR=data
for f in ordpar/tests/test_*.py tests/test_*.py; do python "$f" || echo "FAILED: $f"; done
```

A file also runs on its own: `python ordpar/tests/test_ordpar_links.py`. The root `tests/` folder
holds the test of the correction checks in `handover/checks/`.

Many files test the built site as well as the code: build it first (`build-site.md`), the whole
site (`--all`). After a build of a few articles (`--ids`) those files run and fail on the pages
that are not there; move `ordpar/out/` aside and they are skipped (`ORDPAR_TEST_OUT` is read by
only some of them). A test
that needs something missing (a build, `bun`, Edge, the Bokmålsordboka data) is skipped with the
reason printed, not failed. Tests that read the full Bokmålsordboka data find
`bm-articles.jsonl` through the `mirror` key of `ordpar/local-paths.json` (its shape is
`ordpar/local-paths.example.json`; `ordpar/local_paths.py` reads it).

`python ordpar/deploy.py prepare` runs every file in both folders before a deploy and refuses to
publish on a failure (decisions [103](../../docs/decisions.md#d103); `build-site.md`
§ The deploy). With `--out DIR` it sets `ORDPAR_TEST_OUT`, so the browser tests check the build it
is about to publish.

A few files test tools that only the private repository has: the page where reports and survey
answers are read (`/reports`), its browse server, and the translation pipeline's assessment tool.
Run in the public repository, the tests that need such a module skip, with a reason naming it, and
the rest of the file runs; `export_public.py` runs these files with the others inside the export
and lists them with their counts. The table marks the four files that import one at the top
("Private repository only", or "partly" where the rest of the file runs there too).

## Four ways of running

The table's last column says which:

- **Python**: pure Python over the site's code, synthetic rows, or the built pages in `ordpar/out/`.
- **JS stand-in**: the site's JavaScript run under `bun` (or `node`) against a small stand-in for
  the page. Skipped, with the reason printed, when neither is on `PATH`.
- **bun**: the receiver's and the audio Worker's own tests (`ordpar/receiver/test/`,
  `ordpar/audio-worker/test/`) under `bun test`, wrapped by a Python file. They need bun itself
  (`bun:sqlite`) and are skipped without it.
- **Browser**: headless Microsoft Edge driven over the DevTools protocol
  (decisions [100](../../docs/decisions.md#d100)): what the browser actually draws.

## The browser tests

The browser tests (`test_ordpar_browser_*.py`, and the browser part of
`test_ordpar_changenotice106.py`, the one other file that drives Edge) need Edge, `bun` and a built
site; without one of them they are skipped, with the reason printed. Each file starts one static server on `127.0.0.1`
(a free port) serving `ordpar/out/`, and one headless Edge with a throwaway profile
(`ordpar-test-edge-*`), which is deleted afterwards. Edge and its profile end however the run
ends: a failure, an error in set-up, a timeout or a killed process
(`test_ordpar_browser_cleanup100.py` checks each).

The local server answers as GitHub Pages does: a missing path gets the site's `404.html` with
status 404 (the 404 shell, which serves addresses such as `/bm-en/Norge`), and paths are
case-sensitive (`/bm-en/Norge` is not the folder `norge/`, which a Windows file system would
otherwise find).

The harness is `ordpar/tests/browser/`: `ordpar/tests/browser/harness.py` (the server, Edge,
`Site.check`) and `ordpar/tests/browser/cdp.js` (the DevTools client each check script imports).
A new browser check is a script beside them that imports from `cdp.js` and ends with
`done({...})`, called from a test file with `Site.check("<name>.js", args)`; assert on the returned
dict in Python, so a failure names the page and the case. The harness's docstring has the details.

To run the same checks against the live site, or any other copy:

```bash
ORDPAR_TEST_BASE=https://ordpar.no python ordpar/tests/test_ordpar_browser_senses.py
```

### Environment variables

| Variable | What it does |
|---|---|
| `ORDPAR_TEST_BASE=<url>` | test a served copy (the live site, a preview) instead of the local build |
| `ORDPAR_TEST_OUT=<folder>` | serve or read another built folder instead of `ordpar/out/` |
| `ORDPAR_TEST_OVERLAY=<folder>` | lay a folder over the served build: a path the folder holds (a file, or a folder with its `index.html`) is served from it, every other from the build, `404.html` included. So a few pages rendered into a scratch folder through `build_site.Builder`, with that render's `site/` and `index/`, can be tested without a full build. Matched case-sensitively. |
| `ORDPAR_EDGE=<path>` | another Chromium-family browser |
| `ORDPAR_TEST_SHOTS=<folder>`, `ORDPAR_SHOTS`, `ORDPAR_<n>_SHOTS` | save screenshots, where a file offers it (the table says which) |
| `ORDPAR_TEST_ROOT`, `ORDPAR_TEST_SITE`, `ORDPAR_TEST_SHELL`, `ORDPAR_TEST_INFLECTION` | point a source test at another copy of the repository, of `ordpar/site/`, of `shell.js`, of `inflection.js`, to see it fail on an older version |
| `ORDPAR_TEST_INDEX`, `ORDPAR_TEST_PAGES` | another built search index or set of pages |
| `ORDPAR_MIRROR_DIR` | the folder of Bokmålsordboka's `bm-articles.jsonl`, where `ordpar/local-paths.json` does not give it |

## A fault found gets a test

A fault found in the site gets a test that is shown to fail on the faulty version and pass on the
fix: run it against the live site before the deploy (`ORDPAR_TEST_BASE`), or against a copy of the
repository holding the faulty code. Where a fault cannot be caught mechanically, such as a real
phone's address bar or a question of look, the change's record says so instead.

## Ordbokene's layout beside ours

Ordpar's article card and inflection table follow ordbokene.no's layout
(decisions [102](../../docs/decisions.md#d102)). A script, not a test, compares the two live:
`python ordpar/tests/browser/compare_ordbokene.py` measures ordbokene.no's pages and ours side by
side in headless Edge. It reads the card of *fange* III at 19 window widths and three phone
widths, and the inflection table's layout of three articles at four widths, and prints every
difference beyond 1 px: ordbokene.no against the numbers pinned in
`test_ordpar_browser_cardwidth.py` (has ordbokene.no changed?), and ours against ordbokene.no. Our
deliberate difference, a wide table below 1,024 px where it fits our card, is listed as a note.

| Flag | Measures |
|---|---|
| (none) | `https://ordpar.no` |
| `--local` | the build in `ordpar/out/` |
| `--ours URL` | any copy |
| `--json FILE` | also keeps the raw readings |

It reads only the rendered geometry of ordbokene.no's pages. It is kept out of the test run and out
of `deploy.py prepare`: it loads about forty of ordbokene.no's pages, takes a few minutes and would
fail whenever that site is down. Run it before a deploy. It reports and never blocks; the pinned
numbers change only by a decision. Exit status 0 when nothing differs, 1 when something does, 2
when it cannot run.
